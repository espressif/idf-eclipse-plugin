# AGENTS.md — Espressif-IDE → ESP-IDF VS Code migration

You are migrating **an existing ESP-IDF project**, not creating one. When the user says "Migrate this existing Espressif-IDE project to the ESP-IDF VS Code Extension", perform the configuration migration, not just a review. Keep the human GUI walkthrough out of your response.

## Preserve original configuration

The primary goal is to reproduce the existing Eclipse configuration
in VS Code without changing its behavior.

When an Eclipse setting has a verified VS Code equivalent:

- Extract the original value.
- Apply the corresponding VS Code mapping automatically.
- Preserve custom values exactly unless transformation is required.
- Do not replace explicit values with VS Code defaults.
- Do not ask the user to choose between the original value and a default.

For example, if Eclipse uses:

- GDB port: 3334
- Tcl port: 6667
- Telnet port: 4445

Generate the VS Code configuration using these exact ports.

Only ask the user for clarification when the source configuration is
ambiguous, required information is missing, or a mapping cannot be
determined reliably.

Do not treat existing VS Code defaults or settings generated by an
earlier migration attempt as authoritative over the original Eclipse
configuration.

After generating the configuration, compare all mapped values
against the Eclipse source and report any differences.

The migration should be deterministic and idempotent:
running it again with unchanged source configuration should not
create duplicate debug profiles or change migrated values.

If a matching VS Code debug configuration already exists, update it
instead of creating a duplicate. Preserve unrelated user-defined configurations.

## 1. Discover sources

Find the ESP-IDF project root (containing `CMakeLists.txt`) and the original Eclipse workspace. Inspect the following files where available:

- `sdkconfig`, `dependencies.lock`, CMake/project metadata.
- `<workspace>/.metadata/.plugins/org.eclipse.debug.core/.launches/*.launch` (**E**): use the launch matching the selected project.
- `<workspace>/.metadata/.plugins/org.eclipse.core.runtime/.settings/org.eclipse.launchbar.core.prefs` (**B**): active launch target and associated board.
- `<workspace>/.metadata/.plugins/org.eclipse.core.runtime/.settings/com.espressif.idf.debug.gdbjtag.openocd.prefs` (**D**): fallback workspace debug defaults.
- `<workspace>/.metadata/.plugins/org.eclipse.core.runtime/.settings/com.espressif.idf.launch.serial.ui.prefs` (**S**): optional serial UI state.

Search nearby workspace directories for `.metadata` before declaring it missing. If it is inaccessible, migrate the project-level information and request the workspace path for complete IDE-specific migration; never invent values.

**Precedence by domain:** target: `sdkconfig` → `dependencies.lock` → *active* B → E fallback; board: active B and installed OpenOCD scripts; custom build and debug: project-matching E → D fallback. B may contain entries for many previously selected targets: use the project-qualified `activeLaunchTarget`, not any arbitrary board entry. Never let stale `org.eclipse.cdt.debug.core.target_os` override the real project target.

## 2. Migrate settings.json (Eclipse → VS Code)

Create or **merge** `<project>/.vscode/settings.json`. Preserve unrelated existing settings. Parse E as XML and decode escaped line breaks.

| Eclipse source/key | VS Code key | Operation |
|---|---|---|
| `sdkconfig`: `CONFIG_IDF_TARGET` | No new key required | Preserve project target; don't rewrite `sdkconfig`, `sdkconfig.defaults*` or CMake. |
| E: `com.espressif.idf.launch.serial.core.idfBuildFolderPath` | `idf.buildPath` | Copy explicit directory as a JSON string; verify path usable on current OS. If missing, omit key (defaults to `build`). |
| E: `DFU`, `FLASH_OVER_JTAG` | `idf.flashType` | `DFU=true` → `DFU`; else `FLASH_OVER_JTAG=true` → `JTAG`; else `UART` where values are available. |
| B: active `LaunchTargetManager/.../<...>.board` | `idf.openOcdConfigs` | Find matching board `.cfg` in installed OpenOCD scripts; **verify it exists**. Do not fabricate `board/<target>-builtin.cfg`. |
| E or S: explicitly saved serial port | `idf.port` and optionally `idf.monitorPort` | Only if nonempty and valid on the current machine; otherwise omit (`idf.port` default is `detect`). |
| E: `...gdbServerTclPortNumber` | `openocd.tcl.port` | Convert to integer **and** ensure the OpenOCD server uses `tcl_port N` when customized. |
| E: `...gdbServerGdbPortNumber` | `idf.openOcdLaunchArgs` | Add OpenOCD `-c`, `gdb_port N`; also set debug `target.port` to same port. |
| E: `...gdbServerTelnetPortNumber` | `idf.openOcdLaunchArgs` | Add OpenOCD `-c`, `telnet_port N`. |
| E/D: explicit non-default `...gdbServerExecutable` | `idf.customOpenOCDPath` | Only when resolved executable exists on destination; ignore default `${openocd_path}/${openocd_executable}`. |
| E: explicit non-default `ilg.gnumcueclipse.debug.gdbjtag.svdPath` | `idf.svdFilePath` | Only with resolved, usable path; do not copy `${esp_svd_path}` literally. |

For the abbreviated Eclipse debug keys above, the full prefix is `com.espressif.idf.debug.gdbjtag.openocd.`. Do **not** add undocumented `idf.adapterTargetName` or `idf.monitorEncoding` settings.

**OpenOCD override invariant:** `idf.openOcdLaunchArgs` disables the implicit OpenOCD board/debug arguments. If writing it to support custom ports, explicitly include **both** `"-d${config:idf.openOcdDebugLevel}"` and `"${config:idf.openOcdConfigs,-f}"`, *before* extra `-c` arguments. When Tcl port changes, use `openocd.tcl.port = N` **plus** OpenOCD `-c "tcl_port N"` so client and server agree. Preserve existing custom launch arguments only when compatible; report conflicts rather than silently dropping values.

## 3. Generate or merge launch.json

Create or extend `<project>/.vscode/launch.json`. Prefer a minimal supported **`gdbtarget` + `request: attach`** configuration, not an unverified `type: espidf`:

```json
{
  "version": "0.2.0",
  "configurations": [
    { "name": "ESP-IDF (migrated)", "type": "gdbtarget", "request": "attach" }
  ]
}
```

Map the following only when the source values exist and the active debugger supports them:

| Eclipse `.launch` key | `gdbtarget` destination | Conversion / caveat |
|---|---|---|
| `org.eclipse.cdt.debug.gdbjtag.core.setStopAt` + `.stopAt` | `initialBreakpoint` | `true` → exact symbol; `false` → `""` to disable the default `app_main` break. |
| `com.espressif.idf.debug.gdbjtag.openocd.doStartGdbServer` | `runOpenOCD` | `true` only if using a local OpenOCD server; `false` if managed externally. |
| `com.espressif.idf.debug.gdbjtag.openocd.gdbServerGdbPortNumber` (or consistent CDT `.portNumber`) | `target.host`, `target.port` | Host from explicit Eclipse host or `localhost`; `target.port` is a **string** matching OpenOCD `gdb_port N`. |
| `com.espressif.idf.debug.gdbjtag.openocd.gdbClientOtherCommands` | `preConnectCommands`, `initCommands` or `target.connectCommands` | Split lines; keep semantic timing. `set mem inaccessible-by-default off` may be an init command. `set remotetimeout N` needs **connection-order validation**: extension may insert its own timeout; do not claim guaranteed preservation without testing. |
| `com.espressif.idf.debug.gdbjtag.openocd.otherInitCommands` | `initCommands` when safe | Do not duplicate ESP-IDF's automatically injected reset/flush operations. `{IDF_TARGET_CPU_WATCHPOINT_NUM}` must be resolved, not emitted literally. |
| `com.espressif.idf.debug.gdbjtag.openocd.doFirstReset` / `.firstResetType` / `.doSecondReset` / `.secondResetType` | Connection/reset sequence | Review reset stages separately; no blind 1:1 assignment. |
| `com.espressif.idf.debug.gdbjtag.openocd.doFlashBeforeStart` | **No exact 1:1** | Do **not** automatically set `buildFlashMonitor: true` (adds build+flash+monitor and writes device). |
| `com.espressif.idf.debug.gdbjtag.openocd.doContinue` / CDT `.setResume` | **Review** | Do not infer identical automatic resume behavior from defaults. |

### GDB connection commands

When using the gdbtarget debug adapter with runOpenOCD:

- Always specify the ESP-IDF toolchain GDB.
- Use target.host and target.port for OpenOCD connection.
- Never generate an explicit `target remote` command in
  target.connectCommands or initCommands.
- Do not duplicate connection commands automatically
  managed by the ESP-IDF extension.
- Preserve supported Eclipse custom GDB commands without
  interfering with the extension-managed connection.

For a custom `idf.buildPath`, ensure debugger `program` resolves to the ELF in that directory, not hard-coded `${workspaceFolder}/build`. Use installed extension-supported substitutions or a verified path.

Preserve unrelated user-defined debug configurations. If a matching VS Code debug configuration already exists, update it to match the original Eclipse configuration instead of creating a duplicate. Create a new debug configuration only when no matching configuration exists.

## 4. Non-1:1 settings (report, never invent)

- E: `SERIAL_MONITOR_ENCODING` (e.g. `ISO-8859-1`) — no documented direct VS Code ESP-IDF monitor-encoding key.
- E: `OPEN_SERIAL_MONITOR` — no generic "automatically open Monitor after every flash" equivalent; `idf.launchMonitorOnDebugSession` is debug-specific.
- E: `...enableSemihosting` — no documented direct ESP-IDF extension setting; retain for manual/target-specific OpenOCD review.
- B: adapter serial / USB location selectors (`OPENOCD_ADAPTER_SERIAL`, `OPENOCD_USB_ADAPTER_LOCATION`) — inspect board config and runtime support; do not invent a universal VS Code key.
- E: `...gdbServerOther`, `...jtagFlashArguments` — Eclipse variables/CLI arguments are **not** necessarily VS Code `idf.openOcdLaunchArgs` or `idf.jtagFlashCommandExtraArgs` equivalents.
- Eclipse-only console, CDT index/workbench flags and stale target entries — ignore unless a verified project-level equivalent is needed.

Do not silently drop custom settings: report whether each is **migrated**, **transformed**, **unsupported**, **ambiguous**, or **pending runtime validation**. Do not claim `target.connectCommands` is unsupported: it is documented in ESP-IDF's `gdbtarget` configuration, but order matters.

## 5. Apply, validate and report

1. Back up/inspect pre-existing VS Code files; make only required edits and produce parseable JSON with valid key types. Resolve conflicts **before** modifying anything ambiguous. Do not modify the original Eclipse metadata or project source.
2. Check that the selected target agrees with `sdkconfig` and lockfile; that board config file exists; that GDB/OpenOCD GDB ports match; that Tcl client/server ports match; and that OpenOCD overrides preserve the default board/debug arguments.
3. Check local toolchain and build availability. A successful JSON parse alone does **not** validate OpenOCD/debug behavior. Build validation may run without connected hardware when permitted by the environment.
4. **Never flash/erase a device or start a debug mode that flashes automatically without explicit user approval.** If unavailable or not approved, mark hardware validation **pending**, not failed.
5. Report compactly: files written, mappings applied, unsupported/conflicting items, and checks **passed / pending / not tested**. Do not state that all settings were migrated when unsupported values remain.

**Expected one-line user prompt:** `Migrate this existing Espressif-IDE project to the ESP-IDF VS Code Extension.`

Sources for exact supported destination settings: [ESP-IDF extension settings](https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/settings.html) and [debug configuration](https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/debugproject.html).
